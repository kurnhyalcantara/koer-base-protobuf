# koer-base-protobuf

This repository contains the Protocol Buffer (protobuf) definitions and generated gRPC/HTTP contract code for the **Koer** microservices architecture. It acts as the single source of truth for all service-to-service communication.

## 📂 Repository Structure

```text
.
├── proto/              # Original .proto contract definitions
│   ├── auth-service/   # Proto definitions for Auth Service
│   ├── product-service/# Proto definitions for Product Service
│   └── user-service/   # Proto definitions for User Service
├── gen/                # Autogenerated code output
│   └── go/             # Generated Go packages
├── scripts/            # Build and generation scripts
│   └── generate.sh     # Bash script to generate code for multiple services
├── third_party/        # External protobuf dependencies (e.g. googleapis)
├── go.mod              # Go module config defining this repo as a Go package
├── Makefile            # Make commands for automation
└── README.md           # This documentation
```

## 🚀 Prerequisites and Installation

To contribute or generate code in this repository, you need to install `protoc` (the protobuf compiler) and the corresponding Go plugins.

1. **Install `protoc`**:
   Download the compiler from the [official protobuf releases page](https://github.com/protocolbuffers/protobuf/releases) and add it to your path, or use a package manager:
   - Mac: `brew install protobuf`
   - Linux: `apt update && apt install -y protobuf-compiler`

2. **Install Go Plugins**:
   You can easily install the plugins (`protoc-gen-go` and `protoc-gen-go-grpc`) using the provided Makefile:
   ```bash
   make deps
   ```

## 🛠 Usage & Generation

### Generating Code

To compile the `*.proto` files and generate the Go structs and gRPC network interfaces, you simply need to run the generation script via `make`:

```bash
make generate
```
*(This commands runs `./scripts/generate.sh user-service auth-service product-service` internally).*

If you want to generate code for specific services, you can run the script manually:
```bash
./scripts/generate.sh auth-service product-service
```
This script handles automatically resolving paths, cleaning old generated code, and applying `.proto` changes immediately to the `gen/go/` directories.

### Cleaning

To remove all autogenerated code prior to a fresh generation:
```bash
make clean
```

## 📦 Using as a Go Dependency

To use the compiled protobuf contracts within other Go services across your architecture, you simply need to pull this module.

```bash
go get github.com/kurnhyalcantara/koer-base-protobuf@v1.0.0
```

Inside your service's code, you can then import the generated protobuf models:
```go
import (
    userv1 "github.com/kurnhyalcantara/koer-base-protobuf/gen/go/user-service/v1"
)

// usage example
req := &userv1.GetUserRequest{Id: "123"}
```

## 🏷 Versioning Strategy and Tags

This repository strictly adheres to **Semantic Versioning (SemVer)** (e.g., `v1.0.0`, `v1.1.0`).

### Tagging Workflow

1. Always make your updates on a feature branch and test compilation using `make check`.
2. Once backward-compatible changes are merged into exactly the `main` branch, a formal Release or Tag is created.
3. Services consuming this module can safely target specific tags via `go get github.com/...@vX.Y.Z`.

### Backward Compatibility Rules

- **Never** change the numeric tag of an existing protobuf field.
- **Never** change the type of an existing protobuf field.
- **Never** rename a field and keep the original number.
- Whenever a field is no longer needed, use the `reserved` keyword.

### Handling Breaking Changes

If business logic warrants a paradigm shift that fundamentally breaks compatibility (like redesigning an entire RPC service):
- Create a new version package in the `proto/` folder (e.g., `user-service/v2`).
- Provide alternative RPCs without removing the `v1` implementation immediately. Wait for dependent services to smoothly shift over to `v2`.
- Doing this prevents cascading failures through your microservice architecture.

## ✅ Best Practices

- **Field Numbering Discipline**: Use numbering 1 through 15 for frequently serialized fields (they take 1 byte to encode). Use 16-2047 for less-frequently used parameters.
- **Package Naming**: Always use explicit semantic version packages (`package user.v1;`). Map this cleanly into the `--go_opt` directives by using an explicit `option go_package = "path/to/gen/go/service/v1;pkgname";` in your `.proto` file.
- **Reserved Status**: Rather than commenting out old fields, keep them explicit:
  ```proto
  message User {
      reserved 2, 4 to 6;
      reserved "obsolete_field";
      string id = 1;
  }
  ```
- **Consistent Naming**: 
  - Messages in `PascalCase`.
  - Fields in `snake_case`.
  - Enums and their parameters in `CAPITAL_SNAKE_CASE` (e.g., `ENUM_VALUE_NAME`).
